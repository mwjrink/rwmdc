RWMD · Editor architecture Design for review · not implemented

Small edits. Rebuildable windows. Slug rendering.

Agreed brief

Keep document editing cheap with a small active insertion buffer. Cursor movement does not move text. Rebuild the visible rendering window on edits, reuse it between edits, and estimate scrolling rather than measuring the entire document.

“We can have scroll & cursor position as part of the push constant struct then everything else in buffers with pointers in that struct.”

Edit storage: defer rearrangement until mutation

The active array contains ordinary contiguous text, not a gap. Moving the cursor changes its position only; it does not shift the active suffix or transfer document bytes.

active[60] · 60 bytescursor · 4 bytes
// Proposed CPU layout. Requires a 64-byte-aligned allocation.
typedef struct EditBuffer {
    alignas(64) u8 active[60];
    i32 active_cursor; // Signed offset relative to the active start.

    u8 *before;       // Occupied prefix of a normal growable vector.
    u8 *after;        // Allocation base; occupied bytes end at after_cap.
    u32 before_cap, before_len;
    u32 after_cap, after_len;
    u32 active_len;   // Actual text length, independent of a moved cursor.
} EditBuffer;

// On the current 64-bit target:
_Static_assert(offsetof(EditBuffer, active_cursor) == 60, "hot prefix");
_Static_assert(offsetof(EditBuffer, before) == 64, "cold metadata");
_Static_assert(sizeof(EditBuffer) == 128, "aligned object size");

The first cache line contains payload and cursor, but the complete edit also touches length, revision, and undo metadata. This is a layout decision, not a promise that the transaction executes in one cache line or one instruction. The initial signed-offset design limits documents to INT32_MAX bytes; check sums/capacity growth in wider arithmetic and reject larger files explicitly.

Invariants

  • document = before[0..before_len) + active[0..active_len) + after[after_cap-after_len..after_cap).
  • 0 ≤ active_len ≤ 60; each vector length is within capacity.
  • caret_byte = before_len + active_cursor, calculated in signed wide arithmetic and constrained to [0, document_length].
  • The cursor may be outside the active array after navigation. Do not cast it to an unsigned index or slice with it before materializing that edit position.
  • Byte movement between the three regions preserves the logical text, caret position, and document revision. It is not an edit and does not create an undo record.

Loading and reading

Load a UTF-8 Markdown file directly into the occupied tail of after, with the caret at zero and active/before empty. Use checked allocation growth and complete-read handling; preserve original source bytes and line endings. Unsupported/invalid encoding is a diagnostic, not silent replacement.

Expose logical length, range reads, and a span iterator over the three regions. Parsing/layout may copy the visible region into reusable scratch when a contiguous view is required; do not flatten the whole document on every edit. Borrowed byte spans expire at the next storage mutation. Retained caches use logical offsets or owned data, never pointers into a vector that can move.

Storage is byte-based. Input supplies valid UTF-8; cursor movement and user-facing deletion use grapheme boundaries. Decoder/parser state must survive span boundaries. Undo and serialization operate on logical text; serialization can stream the three spans in order.

Approximate scrolling, stable visible content

No full-document pixel-height measurement is required. The viewport has a logical byte anchor plus a local pixel offset. All rendered coordinates remain local to the prepared window, avoiding large global floating-point positions.

approximate_scroll_fraction = viewport_anchor_byte / document_length
approximate_thumb_fraction  = visible_source_span_bytes / document_length
// Clamp for an empty document, viewport limits, and the UI's minimum thumb size.
  • Use the viewport anchor, not the editing caret. Wheel scrolling must move the thumb even if the caret stays elsewhere.
  • Thumb dragging chooses an approximate source offset, then resolves it to a valid text/layout boundary using parser context.
  • Measured nearby lines may refine the estimate. A better estimate moves the thumb, not the anchored text under the reader.
  • Edits before the anchor adjust its byte offset by the edit delta. If an edit deletes the anchor, choose a surviving boundary in the replacement region.
  • Scrolling within prepared overscan changes push constants only. Crossing the prepared range rebuilds the rendering window.

Overscan is a neighborhood, not “three paragraphs”

Include every paragraph intersecting the viewport, plus a modest before/after margin. A paragraph may itself span the entire document: layout must be able to produce the required wrapped-line range without first measuring every line in that paragraph.

RenderWindow: rebuild on edits, cache between edits

The CPU rendering window is a derived snapshot. Reset and reuse its arena/slab on invalidation. Keep source bytes and document state outside that arena.

Initial invalidation policy

  • Rebuild the whole prepared window for any logical text edit, wrapping-width change, font/layout-style change, or movement outside overscan.
  • Apply all input edits received before a frame, then build one snapshot of the resulting document. Coalescing rebuilds must not drop input or erase undo semantics.
  • Do not rebuild glyph layout for an active-buffer flush, caret movement, caret blink, or scrolling inside overscan.
  • Partial paragraph/run caching is a later optimization only if measured rebuild cost requires it. It does not change the GPU snapshot interface.

Parser context is not global layout

Retain a lightweight block/state index or checkpoints so a window starting inside a fenced code block, list, or quote is interpreted correctly. Do not parse an arbitrary byte slice as an independent Markdown document. An edit to a fence can invalidate context beyond the viewport; propagate parsing until state converges. That propagation can be larger than the layout window and must be measured rather than hidden behind a claimed 1 ms guarantee.

GPU contract: addresses and small view state

Scroll and cursor coordinates are push constants. Geometry, styles, counts, and font data live in GPU buffers. The push header points to the active frame's window data and immutable font data; it never contains CPU document pointers.

// Proposed CPU/GPU ABI, distinct from the current renderer's header.
typedef struct EditorPushConstants {
    VkDeviceAddress window;  // GpuWindowHeader for the selected frame slot.
    VkDeviceAddress font;    // Immutable GpuFontHeader.
    Vec2 scroll_offset;     // Window-local → viewport pixel translation.
    Vec2 cursor_position;   // Window-local caret position, not a byte index.
} EditorPushConstants;
_Static_assert(sizeof(EditorPushConstants) == 32, "push ABI");

GpuWindowHeader

Addresses/counts for glyph instances and decorations, viewport scale, and small style/caret parameters. The caret uses the same scroll transform as the text. Blink/selection changes may update this small per-frame header or decoration range without rebuilding/copying the glyph list.

GpuFontHeader

Addresses for glyph metadata, packed quadratic curves, and band headers/index lists. These are shared read-only resources, independent of document edits and window rebuilds.

Commit and lifetime rules

  1. Acquire a frame slot and wait for its submission fence before CPU writes to that slot.
  2. If the slot has not seen the current window revision, sequentially copy the completed visible glyph/decorations snapshot into its mapped buffers. Otherwise reuse the existing data.
  3. Update small frame parameters and push constants; record Slug rendering using that slot's GPU addresses.
  4. Submit and present. No ordinary-frame device-idle wait and no GPU insert/delete/grow command protocol for document bytes.
  5. Grow a slot's buffer only after that slot is safe to replace. Shared font-buffer replacement must retain old allocations until every referencing frame completes. Never push an address of freed or moved GPU storage.

Keep editing in ordinary CPU-cacheable RAM. Mapped coherent GPU buffers are write destinations, not the source editor data structure. Device-local host-visible memory may be preferred where available; the design does not require ReBAR.

Device addresses are a deliberate GPU-side migration

The current renderer has descriptor-bound draw/metadata buffers and sampled curve/band textures. It does not enable bufferDeviceAddress. This plan interprets “pointers” as VkDeviceAddress, requiring feature negotiation, shader buffer references, VK_BUFFER_USAGE_SHADER_DEVICE_ADDRESS_BIT, and VK_MEMORY_ALLOCATE_DEVICE_ADDRESS_BIT on the relevant allocations.

To make the font path buffer-backed too, store each quadratic as packed half-float coordinate pairs in an aligned integer record; unpack in the shader. Replace texture locations with linear band/curve indexes. Preserve Slug's winding, robust root solver, coverage, and half-float rounding. Validate ABI offsets/alignment and compare pixels and timing against the existing texture path before accepting this migration. Addresses do not inherently guarantee fewer instructions or faster rendering.

Transfer size

250,000 ASCII bytes are about 244 KiB; Unicode source can be larger. That is not the initial GPU upload unit. The current 4K/14 pt workload has about 4,000 visible 24-byte glyph records: approximately 96 KB, or 93.75 KiB, per full glyph-list update. Copy the visible snapshot first; add dirty subranges only when profiling justifies their bookkeeping. A physical edit-buffer flush does not create any upload.

Implementation sequence

1

Logical document storage

Add src/lib/grim/markdown/document.h: the active/before/after representation, checked capacities, UTF-8 loading, logical span reads, cursor positioning, and bulk insert/delete operations. Prove the storage invariants before connecting it to graphics.

2

Edit transactions and parser context

Represent edits as source offset, removed length, and inserted bytes. Maintain document revision, owned undo payloads, viewport-anchor adjustment, and block-state invalidation. Input integration must deliver text, not interpret physical key codes as characters.

3

Visible-window layout

Add src/lib/grim/markdown/layout.h: rebuild the visible neighborhood into reusable line/glyph/hit-test storage. Connect file loading and viewport controls in src/main.c. Preserve source↔display mapping and bounded visible work; do not measure the whole document for the scrollbar.

4

GPU window publication

Adapt render.h, Vulkan buffer helpers, and the Slug shaders to the proposed address-based ABI. Reuse frame-slot revision tracking and synchronization. Migrate font records to buffers in the same clean cutover; do not retain an unmeasured duplicate runtime renderer.

5

Verify the real edit path

Measure storage mutation, parser propagation, window layout, mapped copying, command preparation, and GPU execution separately. Keep the existing visual baseline. Only then decide whether partial layout caching or upload ranges are necessary.

This document defines the storage/rendering architecture. It does not silently expand the current ASCII font cache into complete Unicode shaping, choose Markdown extensions, or implement an IME. Those interfaces must be accounted for as input and layout are connected.

Performance policy

Start with full visible-window rebuild and full visible-list copying on edits. Retain immutable data and unchanged snapshots. Avoid per-glyph allocation and unnecessary global work. Do not assume a cache-line layout, raw GPU pointers, or fewer source-level statements imply a faster application; measure the complete edit path.
